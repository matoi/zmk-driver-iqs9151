# Cross-Pad タイミング判定の分析

## 概要

Cross-pad ジェスチャーでは、左右のトラックパッドの状態を統合して入力の意図を判定する。
しかし、BLE を介した通信には遅延があり、両側の状態が「同時に」揃うことはない。
この非同期性がタイミング判定の根本的な難しさを生んでいる。

本ドキュメントでは、ZMK の hold-tap との構造的な比較を通じて問題を整理し、
通信遅延が存在するシステムにおける同期処理の一般的な課題を考察する。

---

## hold-tap との比較

### 問題構造の共通点

hold-tap も cross-pad も、**入力の意図が即座には確定しない**という同じ本質的な問題を持つ。

| | hold-tap | cross-pad |
|---|---------|-----------|
| 判定対象 | 一つのキーが「タップ」か「ホールド」か | ローカル fc の変化が「単独操作」か「cross-pad の一部」か |
| 確定条件 | 時間経過（tapping-term）または他キー押下 | peer_fc の到着 |
| 不確定期間 | キー押下〜tapping-term 経過 | ローカル fc 変化〜peer_fc 到着（BLE 遅延） |
| 不確定期間の長さ | 設定値（通常 150–300ms）、ユーザーが調整可能 | BLE の通信状態に依存（通常 10–30ms、変動あり）、ユーザーが制御不能 |

### 仕様上の要件の違い

hold-tap と cross-pad では、要件そのものが異なる。
この違いが、hold-tap の既存手法をそのまま適用できない理由でもある。

#### 1. 入力の連続性

hold-tap はキーの press/release という**離散イベント**を扱う。
press と release の間には明確な境界がある。

cross-pad はトラックパッドからの**連続的なフレームデータ**（座標・指本数が毎フレーム流れる）を扱う。
判定を保留している間もデータは到着し続け、それを捨てるか蓄積するかの選択が必要になる。

| | hold-tap | cross-pad |
|---|---------|-----------|
| 入力の性質 | 離散（press/release） | 連続（毎フレームの座標・fc） |
| 保留中のデータ | キー押下イベント 1 件 | フレームデータの連続流（座標移動、fc 変化） |
| 保留のコスト | 低い（イベントをバッファするだけ） | 高い（フレームの破棄はカーソル追従の遅延、蓄積はジャンプの原因） |

#### 2. 確定トリガーの制御可能性

hold-tap では tapping-term-ms をユーザーが設定できる。
使用者の操作の癖に合わせて調整し、誤判定を許容範囲に収められる。

cross-pad の不確定期間は BLE の遅延に依存し、ユーザーは制御できない。
遅延は環境（電波状況、接続間隔）によって変動するため、固定のタイムアウト値で
全ケースをカバーするのが難しい。

#### 3. 判定の構造

hold-tap は**一つの入力ソースに対する判定**である。
split keyboard ではペリフェラルのキーイベントも BLE 経由でセントラルに届くが、
hold-tap が判定するのはあくまで「そのキー自体が tap か hold か」であり、
判定に必要な情報は press/release の離散イベントとタイマーで完結する。
BLE 遅延があってもイベントの順序が保たれれば判定に影響しにくい。

cross-pad は**二つの独立した入力ソースの状態を突き合わせる判定**である。
ローカル側は自身の fc を即座に知れるが、peer の fc は通信を待つしかない。
しかも突き合わせるのは離散イベントではなく、毎フレーム変化する連続的な状態である。
この**情報の非対称性と連続性の組み合わせ**が、hold-tap にはない本質的な制約を生む。

#### 4. フレーバーの適用限界

hold-tap のフレーバー（hold-preferred, tap-preferred, balanced）を cross-pad に当てはめると:

| hold-tap フレーバー | cross-pad での対応 | 限界 |
|---|---|---|
| tap-preferred | **normal-preferred（現状）**: 通常処理を即座に開始し、peer_fc 到着後に切り替え | 切り替え時に cleanup が走り、ゴーストイベントが発生する |
| hold-preferred | **cross-pad-preferred**: peer_fc を待ってから処理を決定 | 単体操作時に毎回遅延。トラックパッドの連続入力では遅延がカーソル追従に直接影響する |
| balanced | peer_fc 到着 or 指リリースで判定 | キーと異なり「リリース」が明確でない場合がある（fc の揺れ）。また BLE 越しの peer_fc 到着は他キー押下より予測困難 |

hold-tap では tap-preferred が「即応性重視」として実用的に広く使われているが、
cross-pad での normal-preferred は cleanup 時のゴーストイベントという
hold-tap の tap-preferred にはない副作用を伴う。
これは、連続入力の途中で処理モードを切り替える必要があるためで、
離散イベントの hold-tap では発生しない問題である。

## 実装が対処しなければならない条件

どの実装方針を取るにしても、以下の条件は避けられない:

| # | 条件 | hold-tap | cross-pad（現状） |
|---|------|----------|-------------------|
| 1 | **モード切り替え時の状態クリーンアップ** | press イベントを遅延送信するだけ。途中まで走った処理が存在しないので、取り消すべき副作用がない | 通常処理が既に走っており、press 済みの BTN を release する必要がある。release 自体が host に見えるイベントになる |
| 2 | **不確定期間中のデータ流入** | press 1 件をバッファするだけ。コストほぼゼロ | 毎フレーム座標・fc が流れ続ける。破棄すればカーソル欠落、蓄積すればジャンプ |
| 3 | **確定トリガーのタイミング制御** | tapping-term-ms をユーザーが設定。人間の操作速度（100ms+）に合わせるので変動を吸収しやすい | BLE 遅延に依存（10–50ms+）。遅延変動が判定ウィンドウと同じ桁で、マージンが取りにくい |
| 4 | **入力の揺れ** | キーの press/release はデバウンス済みで安定 | fc は物理的に不安定（置く途中、端、軽いタッチ）。デバウンスが cross-pad 側の責任 |
| 5 | **通常時のレスポンス** | hold-tap が設定されたキーのみ遅延。他のキーは影響なし | cross-pad 有効時、全てのタッチ開始が影響を受ける可能性がある |

---

## 知見: 通常処理の保留による構造の転換

上記の条件 1・2 が重いのは、現状（normal-preferred）で
**不確定期間中に通常処理を走らせている**ことに起因する。

hold-tap が条件 1・2 を軽くできているのは、
**判定が確定するまで何も出力しない**（press イベントを送信しない）設計だからである。

この知見から、**不確定期間中に通常処理も保留する**設計にすれば、
cross-pad は hold-tap と同じ構造に帰着できる:

| | 現状（normal-preferred） | 通常処理保留方式 |
|---|---|---|
| 不確定期間中の動作 | 通常処理が走る | 何も出力しない（hold-tap と同等） |
| 条件 1: クリーンアップ | press 済み BTN の release が必要 | **解消**: 通常処理が走っていないので取り消すべき副作用がない |
| 条件 2: データ流入 | 通常処理がフレームを消費する | **軽減**: フレームを破棄または軽量にバッファ（hold-tap の press バッファに近い） |
| 条件 3: タイミング制御 | 変わらず | 変わらず（BLE 遅延の変動は依然として制御不能） |
| 条件 4: fc の揺れ | 変わらず | 変わらず（既存の stabilization で対処） |
| 条件 5: レスポンス | 影響なし（即座に処理） | **トレードオフ**: 全タッチ開始に 20–40ms の遅延 |

### 残るトレードオフ

通常処理を保留することで条件 1・2 は解消されるが、条件 5 とのトレードオフが生じる:

- **保留期間中のフレーム破棄**: 20–40ms 分のカーソル移動が失われる。
  ただし指を置いた直後の数フレームは実用上ほぼ無視できる
  （指を置いてから動かし始めるまでに人間側にも僅かな遅延がある）
- **保留の発動頻度**: cross-pad 有効時の全タッチ開始で発動する。
  cross-pad を使わない時間の方が圧倒的に長いため、
  この遅延が単体操作の体感に影響するかは要検証
- **設定による制御**: 保留時間を CONFIG で 0 に設定すれば無効化でき、
  現状の normal-preferred に戻せる

## 通信遅延が存在するシステムにおける同期処理の課題

cross-pad の問題は、より一般的な分散システムの課題の一例でもある。
以下は、BLE に限らず通信遅延のあるシステムで共通する問題を整理したものである。

### 状態の不確定期間（Uncertainty Window）

二つのデバイスの状態を統合して判定するシステムでは、
通信遅延の分だけ「相手の現在の状態がわからない」期間が存在する。

```
デバイス A:  ─── 状態変化 ───────────────────────→
デバイス B:  ─────────────────── 状態変化 ────────→
                                 ↑
                          A はまだ B の変化を知らない
                          （不確定期間）
```

この不確定期間中にデバイス A が行動を起こす必要がある場合、
3 つの戦略がある:

1. **即座に行動する（楽観的）**: 後で修正が必要になるかもしれないが、レスポンスは最速
2. **待ってから行動する（悲観的）**: 修正は不要だが、レスポンスが遅れる
3. **暫定的に行動し、確定後に調整する（投機的）**: レスポンスと正確性のバランスを取るが、実装が複雑

cross-pad の現状（normal-preferred）は戦略 1 に該当し、
cleanup_normal が「後で修正」に相当する。
通常処理保留方式は戦略 2 に該当する。

### 予測不能な遅延変動

BLE の通信遅延は固定値ではなく、接続間隔、電波状況、他の BLE トラフィックによって変動する。

- 通常時: 10–30ms
- 混雑時: 50ms 以上になることもある
- 最悪時: 通知の欠落（到着しない）

固定のタイムアウト値で対処する場合:
- 短すぎる値: 遅延が大きい時にタイムアウトが先に発火し、通常処理に入ってしまう
- 長すぎる値: 単体操作時のレスポンスが常に犠牲になる

hold-tap の tapping-term-ms は人間の操作速度（100ms 以上）に合わせるため、
多少の変動は吸収される。一方、BLE の遅延変動は判定ウィンドウ自体と同じ桁（10-50ms）であり、
マージンが取りにくい。

### 通知欠落の影響

通信遅延だけでなく、通知そのものが欠落する場合がある（→ゴーストジェスチャー問題）。
遅延は「待てば届く」が、欠落は「待っても届かない」ため、
タイムアウトでの fallback が必須になる。
これは hold-tap にはない、通信を介するシステム固有の課題である。

### 状態変化の頻度と通信帯域

トラックパッドは高頻度（100Hz 程度）で状態が変化する。
全ての状態変化を即座に送信できれば遅延は最小化されるが、
BLE の帯域と接続間隔の制約から、全フレームの即時送信は保証されない。

hold-tap では、キーイベントの頻度は人間のタイピング速度（最大でも数十 Hz）であり、
通信帯域が問題になることはまずない。

---

## まとめ

cross-pad のタイミング判定問題は hold-tap と表面的には似ているが、
連続入力・情報の非対称性・遅延の非制御性・通知欠落・高頻度の状態変化という点で本質的に異なる。

しかし、**不確定期間中に通常処理を保留する**ことで、
hold-tap と同じ「確定するまで何も出力しない」構造に帰着でき、
最も重い条件（モード切り替え時のクリーンアップ、データ流入）が解消される。
代償は全タッチ開始時の微小遅延（20–40ms）であり、
これが許容可能かどうかが実装判断の焦点となる。
